# **VoteAssist — Final Database Architecture**

This is the architecture I recommend settling on before we begin implementing the backend. It is designed for the current Victorian election prototype, but should also support federal, state and council elections, multiple candidates per electorate, hundreds of policies, AI research, human reviewers, and historical records.

**Recommended stack: PostgreSQL via Supabase.**

The core design principle is:

> Candidate identity, election participation, sources, evidence, assessments and reviews must be separate records, connected by explicit relationships. Never overwrite published political assessments without preserving their history.

# **1. Architecture overview**

## **VoteAssist data architecture**

**Reference data**

Elections · Parties · Electorates · Policies

**Election participation**

Candidates · Candidate election records · Nominations

**Research**

Sources · Source snapshots · Source links · Evidence

**Assessment & review**

Position assessments · Versions · Reviews · Approval

**Trust & accountability**

Audit events · Change history · Reassessment · Publication

The database is divided into seven logical groups. They can live in the same PostgreSQL database.

| Group          | Purpose                                     |
| -------------- | ------------------------------------------- |
| Reference data | Elections, electorates, parties, policies   |
| Candidate data | People and their participation in elections |
| Research       | Sources and source versions                 |
| Evidence       | Individual claims extracted from sources    |
| Assessments    | Position scores and versions                |
| Review         | Human approval and moderation               |
| Audit          | Immutable record of important changes       |

# **2. Database conventions**

These rules apply to nearly every table.

| Field          | Standard                                        |
| -------------- | ----------------------------------------------- |
| Primary key    | UUID (`id`)                                     |
| Dates          | `timestamptz` in UTC                            |
| Created        | `created_at`                                    |
| Updated        | `updated_at`                                    |
| Deletion       | Prefer archival/soft deletion                   |
| Relationships  | Foreign keys                                    |
| Uniqueness     | Explicit unique constraints                     |
| Validation     | Database constraints plus TypeScript validation |
| Published data | Versioned, not silently overwritten             |
| Status         | Constrained values, not arbitrary strings       |

UUIDs are used for database records. Existing candidate IDs such as `vic-2026-mordialloc-breskin-alex` should be preserved as external/stable identifiers during migration, rather than discarded.

# **4. Candidate data**

## **4.1&#x20;**`candidates`

A person, independent of which election they contest.

| Column               | Type        | Rules    |
| -------------------- | ----------- | -------- |
| `id`                 | UUID        | PK       |
| `display_name`       | text        | Required |
| `given_name`         | text        | Nullable |
| `family_name`        | text        | Nullable |
| `slug`               | text        | Required |
| `profile_image_path` | text        | Nullable |

| `updated_at`         | timestamptz |          |

Candidate identity must not be tied to an electorate, election or party. A person can contest multiple elections, different electorates or change parties.

## **4.2&#x20;**`candidate_elections`

This is one of the most important tables in the entire architecture.

One record per candidate's participation in an election.

| Column                   | Type        | Rules                                                            |
| ------------------------ | ----------- | ---------------------------------------------------------------- |
| `id`                     | UUID        | PK                                                               |
| `candidate_id`           | UUID        | FK → candidates                                                  |
| `election_id`            | UUID        | FK → elections                                                   |
| `election_electorate_id` | UUID        | FK → election_electorates                                        |
| `party_id`               | UUID        | FK → parties, nullable                                           |
| `ballot_position`        | integer     | Nullable                                                         |
| `external_candidate_id`  | text        | Nullable                                                         |
| `candidate_status`       | enum/text   | nominated, confirmed, withdrawn, elected, defeated, disqualified |
| `is_incumbent`           | boolean     | Default false                                                    |
| `official_candidate_url` | text        | Nullable                                                         |
| `nomination_date`        | date        | Nullable                                                         |
| `created_at`             | timestamptz |                                                                  |
| `updated_at`             | timestamptz |                                                                  |

Unique constraint:

`(candidate_id, election_id)`

**Why this matters**

Tim Richardson could contest multiple elections. His candidate identity remains the same, but his electorate, party, nomination status and ballot position may change. This table preserves each election separately.

## **4.3&#x20;**`candidate_party_history`**&#x20;— optional future extension**

This is not required for the first backend launch. Candidate party affiliations in individual elections are already stored in `candidate_elections`.

Add this table only if VoteAssist needs to record party changes between elections, party membership periods or independently sourced historical affiliations beyond election participation.

## **5.3&#x20;**`policy_versions`

Policy propositions need versioning. If wording changes significantly, previously reviewed assessments must not silently apply to the new proposition.

| Column            | Type        | Rules                   |
| ----------------- | ----------- | ----------------------- |
| `id`              | UUID        | PK                      |
| `policy_id`       | UUID        | FK → policies           |
| `version_number`  | integer     | Required                |
| `title`           | text        | Required                |
| `proposition`     | text        | Required                |
| `description`     | text        | Nullable                |
| `response_type`   | text        | Required                |

| `effective_from`  | timestamptz | Nullable                |
| `effective_until` | timestamptz | Nullable                |
| `created_by`      | UUID        | FK → profiles, nullable |
| `created_at`      | timestamptz |                         |

Unique: `(policy_id, version_number)`.

Example:

Version 1 — original

Planning rules should be changed to allow more housing to be built in areas with high housing demand.

Version 2 — future revision

A potential revised proposition, if approved, is stored separately with a new version number. Existing assessments remain linked to Version 1.

## **5.4&#x20;**`policy_version_elections`

| Column              | Type                      |

| `status`            | text                      |
| `created_at`        | timestamptz               |

Unique: `(policy_version_id, election_id)`.

This lets VoteAssist use different policy libraries across elections without losing historical context.

# **6. Source research system**

This is the foundation of the AI research pipeline.

## **6.1&#x20;**`sources`

One record per unique source identity or URL/document reference.

| Column                | Type        | Rules                                                      |
| --------------------- | ----------- | ---------------------------------------------------------- |
| `id`                  | UUID        | PK                                                         |
| `canonical_url`       | text        | Nullable                                                   |
| `source_type`         | enum/text   | Required                                                   |
| `publisher_name`      | text        | Required                                                   |
| `title`               | text        | Nullable                                                   |
| `author`              | text        | Nullable                                                   |
| `published_at`        | timestamptz | Nullable                                                   |
| `first_discovered_at` | timestamptz | Required                                                   |
| `last_checked_at`     | timestamptz | Nullable                                                   |
| `source_status`       | enum/text   | active, unavailable, deleted, restricted, archived         |
| `credibility_class`   | enum/text   | primary, official, reputable_secondary, community, unknown |
| `language`            | text        | Nullable                                                   |
| `content_type`        | text        | Nullable                                                   |
| `created_at`          | timestamptz |                                                            |
| `updated_at`          | timestamptz |                                                            |

Possible `source_type` values:

- candidate_statement
- candidate_website
- party_policy
- parliamentary_record
- media_interview
- news_article
- debate
- community_forum
- questionnaire
- social_media
- official_document
- other

Important: source credibility is not a score of political truth. It is classification of the source's nature and reliability. A candidate's own statement is authoritative for what the candidate said, but not necessarily for whether their factual claims are correct.

## **6.2&#x20;**`source_versions`

Every time content changes or is re-collected meaningfully, preserve a snapshot version.

| Column                | Type        | Rules        |
| --------------------- | ----------- | ------------ |
| `id`                  | UUID        | PK           |
| `source_id`           | UUID        | FK → sources |
| `version_number`      | integer     | Required     |
| `content_text`        | text        | Nullable     |
| `storage_path`        | text        | Nullable     |
| `content_hash`        | text        | Required     |
| `extracted_text_hash` | text        | Nullable     |
| `snapshot_at`         | timestamptz | Required     |
| `published_at`        | timestamptz | Nullable     |
| `extraction_method`   | text        | Nullable     |
| `extraction_status`   | text        | Required     |
| `metadata`            | jsonb       | Default `{}` |
| `created_at`          | timestamptz |              |

Unique:

- `(source_id, version_number)`
- Optionally `(source_id, content_hash)` to avoid storing identical snapshots repeatedly.

The original source should never be silently replaced with a newer version.

## **6.3&#x20;**`source_links`

Links sources to relevant entities without duplicating source records.

| Column                  | Type                                    |
| ----------------------- | --------------------------------------- |
| `id`                    | UUID PK                                 |
| `source_id`             | UUID FK → sources                       |
| `candidate_election_id` | UUID FK → candidate_elections, nullable |
| `party_id`              | UUID FK → parties, nullable             |
| `policy_id`             | UUID FK → policies, nullable            |
| `electorate_id`         | UUID FK → electorates, nullable         |
| `link_type`             | text                                    |
| `attribution_type`      | text                                    |
| `created_at`            | timestamptz                             |

At least one target relationship must be present.

Examples:

- A candidate's interview links to their candidate-election record.
- A party policy page links to the party.
- An article discussing housing may link to the housing policy.
- A community forum page containing responses from multiple candidates can be linked to multiple candidate-election records through multiple rows.

A source is not automatically candidate-specific just because it mentions a candidate.

# **7. Evidence system**

Evidence is the most important part of VoteAssist's research integrity. An evidence record is an individual claim or statement—not an entire article, not an AI summary and not a candidate score.

# **8. Candidate policy assessments**

AI extraction and approved candidate positions must remain separate.

## **8.1&#x20;**`assessments`

Represents the logical assessment of one candidate on one policy version.

| Column                  | Type        | Rules                              |
| ----------------------- | ----------- | ---------------------------------- |
| `id`                    | UUID        | PK                                 |
| `candidate_election_id` | UUID        | FK → candidate_elections           |
| `policy_version_id`     | UUID        | FK → policy_versions               |
| `current_version_id`    | UUID        | FK → assessment_versions, nullable |
| `publication_status`    | text        | Required                           |
| `created_at`            | timestamptz |                                    |
| `updated_at`            | timestamptz |                                    |

Unique:

`(candidate_election_id, policy_version_id)`

This table represents the assessment identity, not its score.

## **8.2&#x20;**`assessment_versions`

Every assessment change creates a new version. This is the authoritative record of the score, reasoning, and approval.

| Column             | Type        | Rules                                                      |
| ------------------ | ----------- | ---------------------------------------------------------- |
| `id`               | UUID        | PK                                                         |
| `assessment_id`    | UUID        | FK → assessments                                           |
| `version_number`   | integer     | Required                                                   |
| `score`            | smallint    | -2, -1, 0, 1, 2 or NULL                                    |
| `rationale`        | text        | Required                                                   |
| `evidence_summary` | text        | Nullable                                                   |
| `coverage_status`  | text        | Required                                                   |
| `confidence`       | numeric     | Nullable                                                   |
| `status`           | text        | draft, submitted, approved, rejected, published, withdrawn |
| `proposed_by`      | UUID        | FK → profiles, nullable                                    |
| `approved_by`      | UUID        | FK → profiles, nullable                                    |
| `approved_at`      | timestamptz | Nullable                                                   |
| `published_at`     | timestamptz | Nullable                                                   |
| `valid_from`       | timestamptz | Nullable                                                   |
| `valid_until`      | timestamptz | Nullable                                                   |
| `change_reason`    | text        | Nullable                                                   |
| `created_at`       | timestamptz |                                                            |

Unique: `(assessment_id, version_number)`.

### **Score constraints**

## **Assessment scoring**

**-2**

Strongly opposes

**-1**

Somewhat opposes

**0**

Neutral / mixed

**+1**

Somewhat supports

**+2**

Strongly supports

**NULL**

Insufficient evidence

Database constraint:

```
CHECK (score IS NULL OR score BETWEEN -2 AND 2)
```

But this alone is insufficient because it allows values like `-1.5` in some types. The column should be `smallint`, and the only valid values must be `-2, -1, 0, 1, 2` or `NULL`.

Also:

- `NULL` is never interpreted as neutral.
- Neutral requires evidence of a neutral position.
- Mixed evidence should be explained.
- Conditional positions must be represented in the rationale.
- An approved version cannot be edited in place.
- A new assessment requires a new version.

## **8.3&#x20;**`assessment_evidence`

Connects an assessment version to the evidence that supports, contradicts or qualifies it.

| Column                  | Type                          |
| ----------------------- | ----------------------------- |
| `id`                    | UUID PK                       |
| `assessment_version_id` | UUID FK → assessment_versions |
| `evidence_id`           | UUID FK → evidence            |
| `relationship`          | text                          |
| `reviewer_note`         | text, nullable                |
| `created_at`            | timestamptz                   |

Relationship types:

- `supports_assessment`
- `contradicts_assessment`
- `qualifies_assessment`
- `context_only`

Unique: `(assessment_version_id, evidence_id, relationship)`.

This is the key traceability link. An assessment must be able to display exactly which evidence was used to reach its conclusion.

# **9. Reviews and approvals**

Review records are separate from evidence and assessments. This prevents approval from simply being a field the AI can set itself.

## **9.1&#x20;**`profiles`

Application users and internal reviewers.

| Column           | Type        | Rules                          |
| ---------------- | ----------- | ------------------------------ |
| `id`             | UUID        | PK; references `auth.users.id` |
| `display_name`   | text        | Required                       |
| `role`           | text        | Required                       |
| `account_status` | text        | active, suspended              |
| `created_at`     | timestamptz |                                |
| `updated_at`     | timestamptz |                                |

Roles:

- `user`
- `researcher`
- `reviewer`
- `senior_reviewer`
- `admin`

Roles must not be freely editable by users themselves. Role changes are controlled by backend permission logic.

## **9.2&#x20;**`reviews`

A general review table for evidence and assessments.

| Column                  | Type        | Rules                                |
| ----------------------- | ----------- | ------------------------------------ |
| `id`                    | UUID        | PK                                   |
| `review_type`           | text        | evidence, assessment, source, policy |
| `evidence_id`           | UUID        | FK, nullable                         |
| `assessment_version_id` | UUID        | FK, nullable                         |
| `source_id`             | UUID        | FK, nullable                         |
| `policy_version_id`     | UUID        | FK, nullable                         |
| `reviewer_id`           | UUID        | FK → profiles                        |
| `decision`              | text        | Required                             |
| `reason`                | text        | Nullable                             |
| `comments`              | text        | Nullable                             |
| `reviewed_at`           | timestamptz | Required                             |
| `created_at`            | timestamptz |                                      |

Exactly one review target must be specified, matching `review_type`.

### **Review decisions**

| Target     | Allowed decisions                             |
| ---------- | --------------------------------------------- |
| Evidence   | approved, rejected, needs_revision            |
| Assessment | approved, rejected, needs_revision            |
| Source     | verified, unverified, unreliable, unavailable |
| Policy     | approved, rejected, needs_revision            |

Review records are append-only. If someone changes their decision, create another review record; don't overwrite the old one.

## **9.3 Publication rules**

An assessment cannot be published unless:

- It has a valid score or `null`.
- It has a rationale.
- It has linked evidence.
- Evidence is reviewed and approved.
- Evidence sufficiently addresses the proposition.
- Source attribution is correct.
- It has passed assessment review.
- The approving reviewer has the correct permissions.
- The required evidence-source threshold has been satisfied or a documented exception approved.
- The proposition version is valid for the election.
- There is no unresolved blocking issue.

The publication process should be enforced server-side, not just by hiding the Publish button in the UI.

# **13. Exact database constraints and integrity rules**

These are requirements, not optional cleanup tasks.

## **Candidate integrity**

- A candidate-election entry must belong to one election.
- The electorate must belong to the same election as the candidate entry.
- A candidate cannot be entered twice in the same election.
- Ballot position must be positive if supplied.
- Withdrawn candidates remain in the database.
- Party affiliations are election-specific.
- Candidate records must not be deleted just because an election is over.

## **Source integrity**

- Source URLs must be normalised before duplicate checks.
- A source can be connected to many candidates.
- Source versions cannot be silently overwritten.
- Content hashes should identify duplicate snapshots.
- Source attribution must be explicit.
- A source being inaccessible does not automatically invalidate previously verified evidence, but it flags it for review.

## **Evidence integrity**

- Evidence must refer to a specific candidate-election record.
- Evidence must refer to a specific policy version.
- Evidence must have a source.
- Evidence excerpt must be traceable to its source or snapshot where possible.
- Party-level evidence cannot silently become candidate-level evidence.
- Rejected evidence cannot support a published assessment.
- AI-generated interpretations must be identifiable as AI-generated.
- Approved evidence cannot be edited in place; revisions should create new records or versions.

## **Assessment integrity**

- One assessment per candidate-election-policy version.
- Only valid score values are permitted.
- `NULL` means insufficient evidence.
- Every published assessment must have a rationale.
- Every published assessment must link to its supporting evidence.
- Published versions must have reviewer approval.
- Assessment revisions must preserve previous versions.
- A policy proposition revision does not automatically transfer old scores.
- Withdrawn assessments remain available internally for audit.

## **Review integrity**

- Reviewer actions are recorded permanently.
- A reviewer cannot approve their own assessment proposal, at least for the standard publication workflow.
- Reviewer roles are controlled server-side.
- Rejection must have a reason where required.
- Approval must refer to the exact assessment version reviewed.

# **14. Supabase security architecture**

The database must not rely on the frontend to protect sensitive records. Permissions must be enforced by PostgreSQL and backend functions.

## **Role permissions**

\| Role | Candidates & policies | Sources & evidence | Assessments | Reviews | Audit |\
\|---|---|---|---|---|\
\| Public | Read public data | Read published evidence | Read published only | No | No |\
\| User | Read | Read published | Read published | No | No |\
\| Researcher | Read | Create/edit drafts | Create draft proposals | Submit for review | Own actions logged |\
\| Reviewer | Read | Approve/reject evidence | Review proposals | Create review decisions | Read permitted history |\
\| Senior reviewer | Read | Review all | Approve/publish/withdraw | Full review control | Read history |\
\| Admin | Manage | Manage | Manage | Manage roles/workflows | Read all |

Important security rules

- Public users must never access unpublished assessment versions.
- Researchers must not be able to approve their own work.
- AI service credentials must never be exposed in the browser.
- Supabase service-role credentials must only exist server-side.
- Users cannot assign themselves reviewer/admin roles.
- Audit history cannot be edited through normal CRUD permissions.
- Database storage of raw source snapshots must have access controls.
- Draft assessments must be excluded from all public API queries.
- Publishing must occur through controlled server-side logic.

## **14.1 Authentication**

Use Supabase Auth for:

- Researcher accounts
- Reviewer accounts
- Admin accounts
- Future optional user accounts for preference saving

Public matching should ideally work without requiring an account.

## **14.2 Row Level Security (RLS)**

Every table needs a deliberate access policy. Do not enable RLS and then accidentally make tables publicly writable.

For example:

- `candidates` — public read.
- `policies` — public read for approved/current policy content.
- `sources` — public read only when linked to published evidence.
- `evidence` — public read only for approved evidence associated with published assessments.
- `assessment_versions` — public read only for published versions.
- `reviews` — private.
- `audit_events` — private.
- `research_jobs` — private.
- `profiles` — restricted.
- `candidate_aliases` — internal read/write initially.
- `import_batches` — internal.

Use database views or controlled RPC functions to expose public information rather than exposing every underlying table directly.

### **Status lifecycle**

| Entity       | Lifecycle                                                            |
| ------------ | -------------------------------------------------------------------- |
| Candidate    | Imported → verified → active → withdrawn/archived                    |

# **19. Critical implementation refinements**

Before calling this architecture final, there are a few technical decisions that should be locked in. These prevent the design from becoming messy once we actually write SQL.

### **A. Avoid unsafe polymorphic relationships**

Tables like `reviews` and `audit_events` reference multiple entity types. PostgreSQL cannot enforce a normal foreign key on a generic `entity_type + entity_id` combination.

**Decision:**

- `reviews`: use explicit nullable target foreign keys and a `CHECK` constraint requiring exactly one target.
- `source_links`: use explicit nullable foreign keys and a `CHECK` constraint requiring exactly one target per row.
- `audit_events`: generic entity reference is permitted because audit events must support any table. Validate entity types in the backend and preserve records even if the original entity is archived.

### **B. Don't use a circular current-version pointer**

The earlier `assessments.current_version_id` proposal would create a circular relationship with `assessment_versions`.

**Decision:** Do not store that pointer initially. Use a controlled view or query to identify the current published assessment version. This avoids circular foreign keys and inconsistent pointers.

### **C. No arbitrary status strings**

Use constrained values for statuses and types. For the initial schema, PostgreSQL `CHECK` constraints are acceptable and easier to evolve than creating dozens of native PostgreSQL enums.

For example:

```
CHECK (
  status IN (
    'draft',
    'submitted',
    'approved',
    'rejected',
    'published',
    'withdrawn'
  )
)
```

### **D. Confidence is not truth**

AI confidence is stored separately from assessment score.

A confidence value of `0.95` must never be interpreted as a 95% probability that the candidate supports a policy. It is a model's extraction confidence unless we specifically build and validate a statistical calibration system.

### **E. Snapshot storage must be deliberate**

We should store extracted text and relevant metadata in PostgreSQL, but potentially large source files in Supabase Storage.

We must respect copyright, privacy, source terms and applicable collection rules. We should not blindly archive every webpage in full.

### **F. Published data is immutable**

The database should enforce the workflow:

- Drafts can be edited.
- Submitted versions are frozen while under review.
- Approved versions are immutable.
- Published versions are immutable.
- Corrections create new versions.
- Withdrawals preserve the old record and require a reason.

# **20. Final architecture decision**

## **VoteAssist database — decisions to lock in**

**Database** — PostgreSQL

**Backend** — Supabase

**Candidate identity** — Separate from election participation

**Policy propositions** — Versioned independently

**Sources** — Stored independently from extracted evidence

**Evidence** — Individual, traceable, reviewable records

**Assessments** — Versioned candidate-policy positions

**Reviews** — Separate from AI extraction and assessment proposals

**Audit history** — Append-only records of consequential changes

**AI research** — Discovery and evidence extraction, never autonomous publication

**Public API** — Controlled views exposing published data only
